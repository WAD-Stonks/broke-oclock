# AI assistance disclosure and assessment boundaries

This repository was initially scaffolded with Hermes Agent assistance at the team's request. AI-assisted portions include workspace/tool configuration (including source aliases, import lint rules and AGENTS.md guidance), generic framework/auth integration boilerplate (including the shared `packages/auth` factory/client extraction), starter pages, shared infrastructure schemas, Express+tRPC health/current-user wiring (including the T3-style move into API-owned routers and a web-owned client) and presentational shell/BootstrapVueNext integration, opt-in Resend/read-only WordPress transport boilerplate, tests, CI and documentation. A later explicit request added the domain Prisma schema (deal/outlet applicability, single User role, review metadata, community records, upload ownership and import provenance) with database regression tests and a protected Better Auth additional role field. This is AI-assisted schema/design work, not student-authored product implementation. Team members must review, understand and maintain these parts, confirm borderline schema assistance with the instructor, and update this disclosure as work changes.

The WAD2 project brief permits assistance for ideation/design inspiration, explanations/debugging hints, starter snippets, test cases/sample inputs/mock data. It prohibits relying on AI for core business logic, backend feature endpoints, critical frontend interactivity and major implementation problem-solving.

The original starter did not implement product workflows. Subsequent user-requested AI-assisted changes added ingestion/parsing/source review and platform-administration endpoints, permission services, schema additions and interactive Vue screens, together with their tests and documentation. These are substantive feature implementations, not just boilerplate, and must not be represented as student-authored work. The stated course restrictions above still apply: obtain instructor clearance before using these AI-assisted features in assessed submission. Student review alone does not establish policy compliance. Remaining deal CRUD, community and discovery work stays student-owned. Earlier feature API proposals are not proof that those remaining workflows exist. The database schema is implemented and tested separately; relations/defaults are not implemented feature functionality. Basic auth/infrastructure examples are reusable boilerplate, not a completed Accounts & Saved feature. AI-assisted UploadThing setup supplies SDK wiring, authentication/origin guards, file policy, a typed browser helper and tests. It deliberately does not implement the assessed Add Deal form, deal-photo attachment workflow, compression flow, moderation or cleanup logic. The later schema provides ownership/attachment fields only; UploadThing callbacks do not persist them automatically. Team members must review the adapter and ask the instructor if its use is borderline.

The user-requested package-manager migration was also AI-assisted tooling work: pnpm workspace/lockfile configuration, runtime separation, lifecycle and audit policy, direct dependency declarations, CI/hosting commands, regression tests and documentation. It does not add assessed product logic.

Vercel assistance additionally supplies project settings, same-origin/SPA routing, an Express export and a self-contained Node ESM build with Prisma engine packaging and isolated runtime tests. The separately approved Node runtime migration replaces legacy execution/build tooling with pinned tsx/esbuild and Node child-process orchestration, removes the runtime bootstrap/lifecycle exception and adds clean-store, signal and standalone production-artifact regressions. No deployment or assessed feature workflow is supplied by that configuration.

Do not remove this disclosure when adding student code. Record what AI supplied and what students authored/reviewed, and include the required disclosure in the final README.txt. Ask the instructor where a borderline use is unclear.
